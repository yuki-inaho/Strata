### Entry 5 (15:45-15:58) prefill チューニング A/B と再起動トラブル
**Findings**
- `--prefill auto:32768` を試行: 16K 読込 2126.6 (前回 2123 と同等)、4K 968 (前回 1071 から微減)。エンジン自身も #669 警告 (借用スロットのエキスパートが RAM に載らず毎チャンク再読込の恐れ) を発出 → **auto に戻した**
- `--conversation-cache-mib 8192` (複数クライアント用) は導入 (害なし・RAM 8GB)
- 再起動1回目が失敗: `native embedding: cannot pin 644 MiB: out of memory`。cgroup 上限 139.4GiB に対し current 133.7GiB (モデル111GBのページキャッシュ) で mlock が失敗

**Tips**
- cgroup 環境ではページキャッシュも「使用メモリ」に算入される。エンジン再起動は他プロセスのキャッシュが落ち着いてから
- 失敗しても数分待って再試行で成功した (current が 115GiB に下がっていた)
- kill -9 直後の再起動では VRAM 未解放で GPU キャッシュ数が一時的に減る (19070→14963) 現象を観測。少し待てば回復

**Struggles**
- 再起動時の OOM 1件 (再試行で解決)
- prefill 32K の A/B (期待した +21-35% は出ず、むしろ僅減 → ロールバック)

### Entry 7 (16:40-17:00) DSV4 (PR #1518) の試行と計測
**Findings**
- モデル UD-IQ1_M (80.9GiB) の DL 完了 (Xet で 205MB/s まで加速)。ファイルサイズが期待値と完全一致
- dsv4_plan: 43層+1, 256エキスパート/top-6, routed 74.42GiB, 非エキスパート 6.51GiB。VRAM プランは expert slots 7,385/11,008 (約67%) + RAM LRU arena 8GiB
- `dsv4_run --selfcheck` on 実GGUF: 全10量子化形式 (F32/Q8_0/Q4_K/Q5_K/Q6_K/IQ2_XXS/IQ3_XXS/IQ1_M/BF16/MXFP4) で finite・平均~0・小さいstd → パス
- 生成品質: 正しい俳句「Silicon dreams, / Parallel paths of light, / Calculations bloom.」を出力 (CPU/CUDA 両方)
- 速度 (18トークンのプロンプト + 生成):
  - CUDA (プロファイルなし): prompt 0.18 tok/s, decode **0.30 tok/s** (hit率97.75%, H2D 40.9GiB)
  - CUDA (プロファイルあり): prompt 0.18 tok/s, decode **0.30 tok/s**
  - CPU + プロファイル (mmap読み): prompt 0.47, decode **0.29 tok/s**
  - CPU + `--expert-ram all` (74.42GiB を RAM 常駐): prompt 0.50, decode **0.59 tok/s** ← 最良
- 支配要因: 1トークンあたり約500回のエキスパート評価×約7MiB。GPU カーネルは未成熟 (GPU hit wait が大きく、H2D 転送も多い)。CPU は single-token の dequant+dot が律速 (~3.5GB/s 実効)
- 結論: **PR は「start porting」段階で、本環境では実用速度に達しない** (Qwen の約1/120)。sm_89 (RTX 4090) 向けに書かれたカーネルで、CMP 170HX (FP 演算が大幅カットされた sm_80) では特に不利と推測。ただし end-to-end で正しい出力が出ることは確認できた

**Tips**
- dsv4_tokenize.py は venv の python で実行する (システム python3 だと regex 欠落)。Strata-dsv4/.venv に regex を追加した
- GPU prefill chunk>=2 は logits が壊れる既知バグ → `--prefill-chunk 1` 必須 (今回の計測もすべて 1)
- CUDA 版は `dsv4_plan` の fixed-cost 見積りでエラーを出すことがあるが、実エンジン (dsv4_run) はロード時に二重計上しないため動く (README 記載どおり)

**Struggles**
- 1回目はトークナイザ依存欠落でプロンプトが空になり、無関係な中国語テキストを生成 (その後修正)
- HF の Xet 切替で旧 .incomplete (11.5GB) が無駄になった
- dq_traits.hpp の定義消失バグ (HEAD) はサブエージェントが前コミットから復元してビルドを通した

## Entry 9 (17:0x-17:3x) 調査: V4.1 の要件はこの環境の2倍以上
**Findings**
- 公式 `deepseek-ai/DeepSeek-V4.1-Flash`: **763B params / 510.3GB / 48シャード**。アーキテクチャ: 552B backbone + 196B Engram (2層のハッシュ参照表202GB)、384 routed experts top-6、FP8 dense + FP4 experts。
- FreeToken (本家/フォーク共通) の V4.1 要件 (`scripts/serve-dsv41-flash.sh` より): チェックポイント **475GiB**、routed experts **269GiB を pinned host RAM**、DSpark 6.7GiB、dense ~12GB GPU、Engram 203GB は NVMe mmap。RAM プリフライトは **MemAvailable ≥ 300GiB** を要求。実測 24.1 tok/s (RTX 5090 + 377GB RAM)。
- 公開されている V4.1 量子化の最小サイズ調査 (完全版のみ):
  | 候補 | サイズ | 判定 |
  |---|---:|---|
  | vcruz305 Q2_K (GGUF) | 264.5GB | ✕ (250GB ディスク) |
  | dongnhdev Q2+EngramQ4 (GGUF) | 267.4GB | ✕ |
  | ds41f-q2 (antirez/DwarfStar用) | 365.7GB | ✕ |
  | buddalaw K160 / K128 (ルーター無効化型) | 365.7GB | ✕ |
  | LibertAIDAI REAP-256E (vLLM用) | 385.5GiB | ✕ |
  | pfeifferj GSQ-RCO-3bit | 415.8GB | ✕ |
  | 公式 safetensors | 510.3GB | ✕ |
  | apetersson MixedQ2 | 169.9GB | △ (Engram 202GB 別途必須 → 実質不可能) |
- **結論: このマシンでは V4.1-Flash は不可能**。ディスク (250GB、3TB RAID md127 はコンテナから bind ファイルしか見えず使用不可) と RAM (cgroup 139.4GiB < 要件 276GiB pinned) の二重ブロッカー。

**Tips**
- PentaCoxian/FreeToken フォークに `scripts/serve-dsv41-flash.sh` と NVMe expert tier (tier3, O_DIRECT + pinned per-layer pools) の実装あり。128GB RAM + NVMe RAID0 で 40 tok/s の正体はこの NVMe tier。
- ただし V4.1 はフルチェックポイント 475GiB が前提で、ディスクが無いとどうにもならない。

**Struggles**
- 250GB ディスクで 264.5GB の最小量子化すら入らない。あと 15-20GB が届かない。

## Entry 13 (19:0x-19:3x) kernel-cache ビルドのバグ修正と複数アーキビルド
**Findings**
- kernel-cache ビルドが `fast_index_copy_240_...` で static_assert 失敗 (kBytes=240 が 128 の倍数でない)。
- 原因特定: `RadixArk/Qwen3.8-Flash-Next-NVFP4` のバンク行サイズ 240/400 バイト(NVFP4 スケール行)がカーネルの不変条件 (`kWorkersFeatures % (16 * worker_threads) == 0`) に違反。DeepSeek-V4-Flash の必要サイズ (262144/524288/4194304/8388608) には影響なし。
- 修正: `kernel/aot.py` にコンパイル可能判定フィルタを追加(240/400 を AOT 対象から除外、他 53 サイズは維持)。コミット 45b5882。
- **fork 改善分を yuki-inaho/FreeToken のブランチ `build-multi-arch-wheels` に push (SSH 経由)**。HTTPS の OAuth トークンは workflow scope 不足で拒否されたため SSH に切替。

**Tips**
- GitHub の HTTPS push は `.github/workflows/*` を含むと `workflow` scope 必須。SSH 鍵なら不要。
- この修正は上流 (FlashML-org) にも出す価値あり(全6アーキの kernel-cache ビルドが壊れるため)。

**Struggles**
- 依存不足3連(huggingface_hub → transformers → freetoken 本体)とカーネルバグ1件を越えて、ようやく全カーネルコンパイル段階に到達。

## Entry 14 (19:3x-20:0x) DSV4-Flash フル常駐は cgroup 139.4GiB では不可能と確定
**Findings**
- 起動ログ: routed experts **143GB (=133.2GiB)** を pinned host RAM にロードする設計。
- 実測3回のロード試行 (並列2回・直列1回) はいずれも **40/43層 (91-93%)** で cgroup 139.19GiB に到達して停止。
  - バンク 124GiB + 諸経費 ~15GiB (torch ランタイム + 未追い出し可能な in-flight ページキャッシュ) ≒ 139GiB。
  - 最後の3層 (約9GiB) がどうしても入らない。cgroup 上限 139.4GiB / swap 0 / memory.max は変更不可。
- 対策として **mem-guard** (5秒毎に page cache を fadvise(DONTNEED) + 閾値超で ft serve を緊急停止) を実装 → 2回目のフリーズは回避できた (ユーザー再起動が必要だった初回の再発防止に成功)。
- 結論: **DeepSeek-V4-Flash-0731 (フル) はこのマシンでは動かない**。理由はディスクではなく cgroup メモリ (設計要件 ~150GiB に対し 139.4GiB)。

**Tips**
- 大モデルのホスト常駐ロード中は「ピン留め + 読み込み中ページキャッシュ」が二重に効いて cgroup を超える。能動的な fadvise と緊急停止ガードが有効。

**Struggles**

## Entry 16 (20:0x-20:2x) 成功: REAP-145B を FreeToken で稼働・tok/s 計測
