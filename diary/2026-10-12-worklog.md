## 定期エントリ (Findings / Tips / Struggles)

### Entry 1 (15:02-15:10) 環境確認とモデル選定
**Findings**
- CMP 170HX 1枚 (sm_80, 64GB VRAM, ヘッドレス)。公式の既成エンジンに sm_80 用がなく、セットアップがソースビルドを実施 (CUDA 12.6, 138ステップ, 約2分で完了)
- モデル選定: 最高品質の **UD-Q4_K_XL (4bit, 111GB)** を選択。--check で RAM 251GB なら全エキスパート (71.7GiB) が RAM に載る判定

**Tips**
- AI エージェント向け手順 `docs/AI_SETUP.md` が優秀。`--check` → `--yes` で非対話セットアップ可能
- `--no-start` でインストールだけ済ませ、起動は後から自分で管理するのが安全

**Struggles**
- なし

### Entry 2 (15:05-15:34) モデルダウンロード (111GB)
**Findings**
- 4シャード計111GB を ~95MB/s で取得。SHA-256 検証 + パック + MTP ドラフト層 (6GB) まで含め約29分

**Tips**
- セットアップは再実行でレジューム可能。切れても同じコマンドで続きから

**Struggles**
- bash ツールのタイムアウトに pip が巻き込まれる等の運用ノイズ (実害なし)

### Entry 3 (15:34-15:37) 初回起動: 予想外の最適構成が自動選択
**Findings**
- 「RAM 71GiB 常駐」を予想していたが、実際は **16.08GiB RAM (page-locked) + 19,070/24,576 エキスパートを GPU キャッシュ** のハイブリッド構成
- 残りエキスパートは GGUF を OS ページキャッシュ経由で読み (実測 100% page cache hit)、実質全量が VRAM+RAM 常駐に近い
- VRAM 使用 64.5/65.5GB、空き 390MiB。STRATA_ROUTE_TAIL_SKIP=7 既定ON、MTP ドラフト有効

**Tips**
- 大容量 VRAM 機ではエンジンが「GPU キャッシュ最大化 + RAM は補完」を自動で舵取りする。ユーザー側の手動調整は不要だった

**Struggles**
- なし

### Entry 4 (15:37-15:40) 公式ベンチマーク
**Findings**
- chat decode **64.6 tok/s** (45.9-82.4, n=9)、TTFT 0.52s
- プロンプト読込: 4K 1071 tok/s / 16K **2123 tok/s** (TTFT 7.59s)
- agent セッション: decode **71.4 tok/s**、会話キャッシュヒット 68.8%
- 公式ドキュメントの予想 (64GB RAM + 12GB GPU で 7-8.5 tok/s) の**約8〜10倍**。64GB VRAM + 251GB RAM + ページキャッシュの効果が支配的

**Tips**
- `bench.sh` は起動済みサーバを自動検出してそのまま計測 (133秒で完了)。結果は bench/results/…/README.md に定型レポート出力

**Struggles**
- chat decode の分散が大きい (45.9〜82.4)。起動直後はキャッシュ適応に時間がかかり遅い。warm-up 後に安定

### Entry 5 (15:45-15:58) prefill チューニング A/B と再起動トラブル
**Findings**
- `--prefill auto:32768` を試行: 16K 読込 2126.6 (前回 2123 と同等)、4K 968 (前回 1071 から微減)。エンジン自身も #669 警告 (借用スロットのエキスパートが RAM に載らず毎チャンク再読込の恐れ) を発出 → **auto に戻した**
- `--conversation-cache-mib 8192` (複数クライアント用) は導入 (害なし・RAM 8GB)
- 再起動1回目が失敗: `native embedding: cannot pin 644 MiB: out of memory`。cgroup 上限 139.4GiB に対し current 133.7GiB (モデル111GBのページキャッシュ) で mlock が失敗

**Tips**
- cgroup 環境ではページキャッシュも「使用メモリ」に算入される。エンジン再起動は他プロセスのキャッシュが落ち着いてから
- 失敗しても数分待って再試行で成功した (current が 115GiB に下がっていた)
- kill -9 直後の再起動では VRAM 未解放で GPU キャッシュ数が一時的に減る (19070→14963) 現象を観測。少し待てば回復

**Struggles**
- 再起動時の OOM 1件 (再試行で解決)
- prefill 32K の A/B (期待した +21-35% は出ず、むしろ僅減 → ロールバック)

### Entry 6 (15:58-16:40) 復帰確認と DSV4 並行準備
**Findings**
- 最終設定で再起動成功 (loaded: true)。22K トークンプロンプトを 1710 tok/s で読み、"OK" と正答
- DSV4: サブエージェントが PR #1518 を調査・ビルド成功 (ローカル修正1点: dq_traits.hpp の定義消失を復元)。GPU prefill chunk>=2 に既知バグ → `--prefill-chunk 1` を使用予定
- DSV4 モデル DL は当初の hf_transfer 経路が途中で死亡 (0MB/min で停止) → Xet 高速転送 (HF_XET_HIGH_PERFORMANCE=1) で再開、~64MB/s

**Tips**
- 2026年の Hugging Face は Xet 転送。`HF_HUB_ENABLE_HF_TRANSFER=1` は無効 (非推奨警告)。`HF_XET_HIGH_PERFORMANCE=1` を使う
- 長時間ダウンロードは `setsid` でプロセスを分離するとツールのタイムアウトに巻き込まれない

**Struggles**
- バックグラウンド DL がツールタイムアウトで死亡する問題 → setsid で安定化
- Xet 切替で旧 `.incomplete` (11.5GB) が再開されず、実質やり直しになった (ロス)

### Entry 7 (16:40-17:00) DSV4 (PR #1518) の試行と計測
**Findings**
- モデル UD-IQ1_M (80.9GiB) の DL 完了 (Xet で 205MB/s まで加速)。ファイルサイズが期待値と完全一致
- dsv4_plan: 43層+1, 256エキスパート/top-6, routed 74.42GiB, 非エキスパート 6.51GiB。VRAM プランは expert slots 7,385/11,008 (約67%) + RAM LRU arena 8GiB
- `dsv4_run --selfcheck` on 実GGUF: 全10量子化形式 (F32/Q8_0/Q4_K/Q5_K/Q6_K/IQ2_XXS/IQ3_XXS/IQ1_M/BF16/MXFP4) で finite・平均~0・小さいstd → パス
- 生成品質: 正しい俳句「Silicon dreams, / Parallel paths of light, / Calculations bloom.」を出力 (CPU/CUDA 両方)
- 速度 (18トークンのプロンプト + 生成):
  - CUDA (プロファイルなし): prompt 0.18 tok/s, decode **0.30 tok/s** (hit率97.75%, H2D 40.9GiB)
  - CUDA (プロファイルあり): prompt 0.18 tok/s, decode **0.30 tok/s**
  - CPU + プロファイル (mmap読み): prompt 0.47, decode **0.29 tok/s**
  - CPU + `--expert-ram all` (74.42GiB を RAM 常駐): prompt 0.50, decode **0.59 tok/s** ← 最良
- 支配要因: 1トークンあたり約500回のエキスパート評価×約7MiB。GPU カーネルは未成熟 (GPU hit wait が大きく、H2D 転送も多い)。CPU は single-token の dequant+dot が律速 (~3.5GB/s 実効)
- 結論: **PR は「start porting」段階で、本環境では実用速度に達しない** (Qwen の約1/120)。sm_89 (RTX 4090) 向けに書かれたカーネルで、CMP 170HX (FP 演算が大幅カットされた sm_80) では特に不利と推測。ただし end-to-end で正しい出力が出ることは確認できた

**Tips**
- dsv4_tokenize.py は venv の python で実行する (システム python3 だと regex 欠落)。Strata-dsv4/.venv に regex を追加した
- GPU prefill chunk>=2 は logits が壊れる既知バグ → `--prefill-chunk 1` 必須 (今回の計測もすべて 1)
- CUDA 版は `dsv4_plan` の fixed-cost 見積りでエラーを出すことがあるが、実エンジン (dsv4_run) はロード時に二重計上しないため動く (README 記載どおり)

**Struggles**
- 1回目はトークナイザ依存欠落でプロンプトが空になり、無関係な中国語テキストを生成 (その後修正)
- HF の Xet 切替で旧 .incomplete (11.5GB) が無駄になった
- dq_traits.hpp の定義消失バグ (HEAD) はサブエージェントが前コミットから復元してビルドを通した

### Entry 8 (17:00-17:05) 最終状態の復旧
**Findings**
- DSV4 のページキャッシュを `posix_fadvise(DONTNEED)` で追い出し (cgroup current 133→22GiB) → Qwen を問題なく再起動できた
- Qwen 最終稼働確認: loaded=true, VRAM 64.5GB, 追加計測 decode 45.1 tok/s (81トークン, キャッシュ適応途中の値。ベンチ中央値は 64.6)

**Tips**
- cgroup 環境での再起動前は、不要になった大ファイルのページキャッシュを fadvise で追い出すと mlock 失敗を予防できる

**Struggles**
- 停止時に orphan エンジンプロセスが VRAM を握り続ける事象が1回 (PID を直接特定して解決)
