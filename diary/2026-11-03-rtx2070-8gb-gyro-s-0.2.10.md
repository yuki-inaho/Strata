# 作業記録: Strata 0.2.10 を 8GB カードと 24.5GB の RAM で試す (2026-11-03)

> 個人情報とローカルパスを除去して diary/ に収録 (2026-11-03)。手順は
> [再現手順書](2026-11-03-8gb-gyro-s-runbook.md) にまとめた。

0.2.10 のリリース文は「Qwen3.8-Flash-Next が 8GB カードで 20+ tok/s」と「並列性の大幅な改善」を
うたっている。この機体で実際に起動して計測し、どこまで再現できるかを確かめた。数値はすべて実測で、
エンジン自身がログに出す値を使っている。

## 環境

| 項目 | 値 |
| --- | --- |
| 本体 | 小型デスクトップ、Intel Core i7-9750H (6C/12T) |
| GPU | NVIDIA GeForce RTX 2070 8GB（sm_75、Turing）、driver 580.178.04 |
| RAM | 24.5GB（MemAvailable は 12〜14GB） |
| ディスク | NVMe 3.7TB（空き 617GB）、エンジンの計測で 2.50 GB/s |
| PCIe | host から device へ 12.2 GB/s（エンジンのプローブ値） |
| OS | Ubuntu Linux 6.8.0-147 (x86_64) |
| Strata | Terminal 0.2.10（Control 0.1.56）と engine 0.1.56 linux-x86_64-cuda-cuda13 |

`strata doctor` は ok を返した。エンジンは署名付きフィードから 668MB を取得して自動で入った。
sm_75 用のコードは CUDA 13 パッケージに含まれているので、自分でビルドする必要はなかった。

## モデルの選定

8GB の VRAM と 24.5GB の RAM では、IQ3_S (84GB)、IQ2_XS (68GB)、Q2_0 (66GB) のどれもプランが
「does not fit this computer」と警告する。警告なしで通ったのは、Qwen3.8-Flash-Next 系で最小の
Gyro-S (TQ1_0、ダウンロード 58.5GB、実メモリ 27.6GB) だけだった。ここでは Gyro-S を選んだ。

```
strata launch --plan --model gyro-s --family gyro --context 128k
  model     Qwen3.8-Flash-Next (Gyro) Gyro-S, 58 GB
  context   128K    pictures on (the reader runs on the processor)    parallel fit to your card
  drafting  DFlash2 (its drafter is downloaded first)
```

## 起動

```sh
sh install.sh
strata launch --model gyro-s --family gyro --context 128k --vision cpu \
  --drafting auto --tune skip --yes --no-tui
```

ダウンロードは 59.4GB で、モデル 58.5GB、画像リーダー 0.9GB、DFlash2 1.2GB の合計だ。回線は 35〜43MB/s
で、約 30 分かかった。初回はこのあとに experts を 1 ファイルにまとめるパック作成（26GB）と
DFlash2 の変換が入り、数分で終わる。

ロードは 15 秒で終わった。ただしこれは page cache と mmap のおかげで、重みがすべて常駐したわけではない。

## 起動時に働いた低メモリの経路

要求した context は 131072 で、起動後もそのまま維持された。エンジンは context を縮めず、次の段で
メモリを逃がしている。以下はエンジンログの実値だ。

- `KV streaming: 20480 of 131072 cells per QSA layer in VRAM, the K/V in 1.55 GiB of pinned RAM`。
  KV の窓を 20,480 に落とし、残りは pinned RAM に置いてストリームする。
- `expert cache 445 slots, 0.43 GiB of VRAM`。24,576 のランクのうち VRAM に載るのは 445 で、1.8% にあたる。
  残りは SSD から都度読む。
- `short of GPU memory: ... the loan keeps 16`。プロンプト経路に貸すスロットを 16 に縮め、
  プロンプトを 256 トークン刻みで読む。
- `prefill plan: ... about 3346.6 GB read from the drive per 32768-token prompt`。32K のプロンプト 1 本で
  3.3TB を読む計算になる。RAM が足りない機体の限界がここに出ている。
- `WARNING: only 504 MiB of VRAM free ... (#2065)`。エンジン自身が `--vram-reserve-mib 704` を勧めている。
- `--draft dflash2: on a 12 GB NVIDIA card the MTP drafter was faster ...; continuing as asked`。
  8GB と sm_75 の組み合わせは未計測だが、Auto のまま DFlash2 をロードした（625MiB、selector は Q4_0）。
- `no MTP layer is loaded` と `Strata set this model to one request at a time`。0.2.10 の
  「ドラフターは 1 本だけ」「DFlash2 は 1 リクエスト」がそのまま効いている。

## 計測

| 項目 | 結果 |
| --- | --- |
| 60 トークン（暖機後、55 を再利用） | 54 生成 / 5.76 秒 = 9.4 tok/s、DFlash2 は 36 本中 28 本を採用 |
| 1,653 トークンのプロンプト | 36.2 秒で読み込み（45.7 tok/s）、生成 8.2 tok/s、この 1 本で SSD から 25.1GB |
| 17,948 トークン（opencode の初回） | 481 秒で読み込み（37.3 tok/s）、生成 10.5 tok/s |
| 18,095 トークン（2 ターン目） | 18,050 を再利用し、45 だけ読んで 3.4 秒、生成 11.8 tok/s |
| 画像（CPU リーダー、896x448） | 15.9 秒で「4217: red, blue」と正答 |
| 同時 2 リクエスト（slot=1） | 8.6 秒と 13.0 秒で完了し、直列に処理された |
| セッション累計の SSD 読み込み | 1.55TB（起動から十数リクエストの時点） |

暖機後の decode は 9〜12 tok/s、prefill は 37〜46 tok/s だった。同じ機体で 20 tok/s は出ない。

## opencode に繋ぐ

`strata connect opencode --check` は 2 件とも ok だった。prompt は 7.1 秒で pong を返し、tool call は
21.9 秒で `get_weather {"city":"Paris"}` を返した。

実機の OpenCode は v2.1.3 で、`strata connect opencode` が印字する設定（`npm`、`options`、`tool_call`
という旧フィールド形）でもプロバイダを登録できた。#4528 が cannot reproduce で閉じているのと一致する。

ただし既定の `limit.output: 4096` は未解決の #5006 で、長いセッションでは compaction が 4096 で切れて
`Compaction summary reached the output token limit` になる。#5006 の推奨に従い、`output` を 16384、
`input` を 114688、`compaction.buffer` を 24576 に変えて使った。設定はプロジェクト単位の
`opencode.jsonc` に置き、グローバル設定は触っていない。

実際に走らせたコマンドは次のとおり。

```
opencode run --model strata/qwen3.8-flash-next-gyro-gyro-s --auto \
  "Read the file notes/key.txt in this folder and reply with only the access code."
→ Read notes/key.txt → ZX-4419   (8 分 44 秒、うち初回の prefill が 481 秒)
```

ツール呼び出し、結果の受け取り、回答まで通り、opencode との連携は成立した。1 回目のプロンプトは
17,948 トークンで、その大半は opencode のシステムプロンプトとツール定義だ。

## わかったこと

8GB カードで 128K の context が起動するのは本当で、0.2.10 のメモリ段は設計どおりに動く。ただしこの機体では
カードではなく RAM 24.5GB が足を引っ張り、expert の 98% が SSD 読みになる。その結果、decode は 9〜12 tok/s、
prefill は 37〜46 tok/s に落ちる。20+ tok/s は RAM 64GB 級の話で、リリース本文の 63〜73 tok/s も
「大きいカードを手で 8GB に絞った、RAM に余裕のある検証機」の数字だ。実 8GB カードの A750 が
12.7〜14.8 tok/s だったという記載に近い側だと確認できた。

長いプロンプトの速さは I/O で決まる。1.6K トークンで 25GB、32K で 3.3TB の読み込みを見込むため、
エージェント用途では 1 ターンが 8 分級になる。実測でも 8 分 44 秒のうち 8 分が prefill だった。

並列性の改善（all-cards split）は、sm_86 か sm_120 のカード 2 枚、または R9700 の 4 枚が条件で、
1 枚のこの機体は対象外だ。代わりに「DFlash2 は 1 リクエスト」が効いて、同時 2 本が直列になるのを確認した。
MTP にすれば複数 slot になるが、MTP 層 5.2GB の追加ダウンロードが要るので今回は試していない。
