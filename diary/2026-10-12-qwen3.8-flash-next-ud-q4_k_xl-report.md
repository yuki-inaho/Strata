# レポート: Strata で Qwen3.8-Flash-Next を動かす (CMP 170HX / 2026-10-12)
> 個人情報(ホームディレクトリ等)を除去して diary/ に収録 (2026-10-12)。

## 0. 結論 (要約)

- **Qwen3.8-Flash-Next (Unsloth UD-Q4_K_XL, 約4bit, 111GB)** を Strata v0.1.43 でこの環境に導入し、正常動作を確認した。
- **速度 (公式ベンチ, 3回計測の中央値)**: チャット生成 **64.6 tok/s** (範囲 45.9–82.4) / エージェント風セッション **71.4 tok/s** (48.1–83.6) / 16K トークンのプロンプト読込 **2,123 tok/s**。
- 公式ドキュメントが 64GB RAM + 12GB GPU 環境で「7–8.5 tok/s」としていた UD-Q4_K_XL が、本機 (VRAM 64GB + RAM 251GB) では**約8〜10倍**の速度で動作。エンジンが 24,576 エキスパート中 **19,070 個 (約78%) を VRAM キャッシュに自動配置**し、残りも page-locked RAM + OS ページキャッシュに載る構成が効いた。
- **PR #1518 (DeepSeek-V4-Flash ポーティング) も試した**: ローカル修正1点でビルド成功、自己診断・生成ともに成功し正しい出力を確認。ただし速度は最良 0.59 tok/s (CPU) / 0.30 tok/s (CUDA) で、**初期ポート段階のため実用速度には達しない**。
- **yuki-inaho/Strata フォーク**: 上流 (Niko1221/Strata) と HEAD ハッシュまで完全同一で、独自変更ゼロ。取り込むものはなかった。

## 1. 環境

| 項目 | 値 |
| --- | --- |
| GPU | NVIDIA CMP 170HX ×1 (VRAM 64 GiB, compute capability 8.0 / sm_80, ヘッドレス) |
| GPU ドライバ / CUDA | 610.57.04 / toolkit 12.6 (既成エンジンが無くソースビルド) |
| CPU / RAM | AMD EPYC 7663 56C/112T (AVX2) / 251 GiB |
| ストレージ | Samsung NVMe SSD 238GB |
| その他 | Linux (コンテナ), cgroup メモリ上限 139.4 GiB, sudo 不可 |

補足: CMP 170HX は Strata の公式サポート一覧 (RTX 20〜50 系など) に無いが、sm_80 向けのソースビルドで問題なく動作した。PCIe 2.0 x16 (推定 ~8GB/s) は公式比で不利な条件。

## 2. やったこと (概要)

1. `Niko1221/Strata` を clone し、`./setup.sh --check` で適合判定
2. 最高品質モデル **UD-Q4_K_XL** を選択して非対話セットアップ (`--yes --family unsloth --model UD-Q4_K_XL --no-start`)
   - CUDA エンジンをソースビルド (138ステップ, 約2分)
   - モデル 111GB + MTP ドラフト層 6GB を取得 (約29分, 途中 ~95MB/s)
3. サーバー起動 → `/health`, `/v1/models`, チャット動作検証
4. 公式ベンチ `bench.sh` 実行 (133秒) → 定型レポート生成
5. チューニング A/B (`--prefill auto:32768` を試してロールバック、`--conversation-cache-mib 8192` を採用)
6. PR #1518 を別ディレクトリに clone・ビルド (ローカル修正1点)・自己診断・生成・速度計測
7. yuki-inaho/Strata フォークの差分調査 (結果: 独自変更ゼロ)
8. 最終状態で Qwen サーバーを再起動し稼働中

## 3. Qwen3.8-Flash-Next の実行構成

最終設定 (`Strata/strata-unsloth-ud-q4_k_xl.json`):

```
--pack unsloth-ud-q4_k_xl --native Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf
--expert-profile expert-profile.bin --expert-cache auto --prefill auto
--spec 4 --spec-min-p 0.5 --mtp mtp/rt --max-context 32768 --kv int8
--resident-budget-gib 71 --conversation-cache-mib 8192
```

エンジンが起動時に自動選択した配置 (ログより):

- **resident RAM mode: 16.08 GiB of experts in RAM (page-locked), 19,070 / 24,576 in the GPU cache**
- 残りのエキスパートは GGUF を OS ページキャッシュ経由で参照 (実測 100% page-cache hit、0 file reads 運用)
- VRAM 使用 64.5 / 65.5 GiB (空き 390 MiB)、STRATA_ROUTE_TAIL_SKIP=7 (既定ON)、MTP ドラフト有効、prompt chunk 8,192

つまり「71GiB を RAM 常駐」という当初予想ではなく、**大容量 VRAM を持つ機体ではエンジンが「GPU キャッシュ最大化 + RAM は補完」へ自動で舵を切る**。これが高速化の主要因。

### 公式の予想との比較

Strata 公式ドキュメントは UD-Q4_K_XL について「64GB PC + 12GB GPU で 7–8.5 tok/s (専門家の多くを SSD から読むため)」としている。本機は VRAM 64GB + RAM 251GB により SSD 読みがほぼ発生せず、**約8〜10倍**の 64.6〜71.4 tok/s を達成。

## 5. PR #1518 (DeepSeek-V4-Flash ポーティング) の試行

やったこと:

- `perronemirko/Strata` の `deepseekv4-flash` ブランチ (HEAD `3cfae93`) を別ディレクトリに clone
- **ビルド修正1点**: HEAD で `dsv4_ext/include/dsv4/dq_traits.hpp` のヘルパ関数定義が消失 (Doxygen リファクタで壊れた)。前コミット `76af7951` の定義を復元してビルド成功 (CUDA 12.6, sm_80, g++ 13.3)
- モデル `unsloth/DeepSeek-V4-Flash-GGUF` の UD-IQ1_M (80.9 GiB, 3シャード) を取得
- `dsv4_plan`: 43層+1, 256 experts/top-6, routed experts 74.42 GiB、VRAM スロット 7,385/11,008 (約67%)
- `dsv4_run --selfcheck`: 実 GGUF の全10量子化形式 (F32/Q8_0/Q4_K/Q5_K/Q6_K/IQ2_XXS/IQ3_XXS/IQ1_M/BF16/MXFP4) で統計正常
- 生成品質: 俳句「Silicon dreams, / Parallel paths of light, / Calculations bloom.」を CUDA/CPU 両方で確認

速度計測 (同じ 18トークンプロンプト + 16〜19トークン生成):

| 構成 | prompt | decode |
| --- | ---: | ---: |
| CUDA, プロファイルなし | 0.18 tok/s | 0.30 tok/s |
| CUDA, プロファイルあり | 0.18 tok/s | 0.30 tok/s |
| CPU, mmap 読み | 0.47 tok/s | 0.29 tok/s |
| **CPU + `--expert-ram all` (74.4GiB RAM 常駐)** | 0.50 tok/s | **0.59 tok/s** |

- ボトルネック: 1トークンあたり約500回のエキスパート評価 × 約7MiB。CUDA カーネルは未成熟 (GPU 待ち + H2D 転送過多)、CPU は single-token の dequant+dot が律速 (実効 ~3.5GB/s)。
- 注意: GPU prefill は chunk≥2 で logits が壊れる既知バグがあるため、すべて `--prefill-chunk 1` で計測。
- **結論: PR は "start porting" の初期段階。end-to-end では動くが、本環境では実用速度に達しない** (Qwen の約 1/120)。作者は sm_89 (RTX 4090) + CUDA 12.8 でテストしており、FP 演算を大幅にカットした CMP 170HX (sm_80) は特に不利。改善の余地は大きい (バッチ prefill の修正、GPU カーネル最適化、プロファイル設計)。

## 8. ハマりどころ (Tips 集)

- **cgroup 環境ではページキャッシュも「メモリ使用量」**: モデル111GB のキャッシュで cgroup 上限 (139.4GiB) が逼迫すると、再起動時の mlock (RAM 常駐化) が失敗してエンジンが落ちる。不要になった大ファイルは `posix_fadvise(DONTNEED)` で追い出すと予防できる (実際に 133→22GiB まで回復させて復帰成功)。失敗しても数分待って再試行で改善する。
- **停止時に orphan エンジンが VRAM を握り続けることがある** (`nvidia-smi --query-compute-apps` で PID 特定して直接 kill)。
- **Hugging Face は 2026 年時点で Xet 転送**: `HF_HUB_ENABLE_HF_TRANSFER=1` は非推奨で無効。`HF_XET_HIGH_PERFORMANCE=1` を使う (有効化後は ~205MB/s)。
- **長時間ダウンロードは `setsid` でプロセス分離**するとツールのタイムアウトに巻き込まれない。
- **DSV4 側**: `tools/dsv4_tokenize.py` は venv の python で実行 (システム python3 は regex 欠落)。`--prefill-chunk 1` 必須。

## 9. 再現手順 (主要コマンド)

```sh
# セットアップ (非対話)
git clone https://github.com/Niko1221/Strata.git && cd Strata
./setup.sh --check
./setup.sh --yes --family unsloth --model UD-Q4_K_XL --no-start   # 111GB DL + エンジンビルド

# 起動 / 検証 / ベンチ
./run-unsloth-ud-q4_k_xl.sh &        # サーバー (8080)
curl http://127.0.0.1:8080/health
./bench.sh                            # 公式ベンチ (~133秒)

# API 例
curl http://127.0.0.1:8080/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"strata","messages":[{"role":"user","content":"Hello"}],"max_tokens":128,"reasoning_effort":"none"}'
```

## 10. 制約・未確認

- 速度はエンジン自身の timings に基づく。正確性の検証 (llama.cpp との logits 比較) は未実施。
- `--calibrate` による更なる最適化、`--parallel`(同時リクエスト)、128K コンテキスト化は未実施 (必要なら設定変更のみで可能)。
- CMP 170HX は公式サポート外。長時間連続稼働の安定性評価は限定的 (ベンチ〜数十分の範囲では安定)。
- DSV4 は WIP ポートであり、速度・品質の網羅検証は限定的 (短い生成のみ)。
